What this system is built from, and how the pieces talk

One application, four runtimes it depends on. The pipeline itself is a single labelled box, the way a real stack diagram treats an app — everything inside it is a library the app imports, not a list of its own source files pretending to be dependencies.

Python runtime external network service JVM / Node — the CQL engine storage / local data dev & deploy tooling

Why the pipeline is one box, not five

Earlier drafts of this diagram listed segment.py, bind.py, gate.py as if each were a dependency the way z3-solver is. They are not — they are the application itself. A stack diagram shows what a system is built on; the system's own modules belong inside one labelled box, exactly as "Backend" is one box built on Python/Flask rather than five boxes named after its own route files.

The only non-deterministic boundary

Every model call crosses exactly one API. Everything else in this diagram — the solver, the terminology cache, the CQL engine — is deterministic and runs offline, which is what cassette.py exists to exploit: replay the tape, skip the boundary entirely.

Two runtimes for one language target

cql-execution is JavaScript and consumes only ELM; ELM only exists once HL7's own Java translator has run. Turning a CQL string into something executable is unavoidably a two-runtime operation, not a design choice.

The cache is the version pin

A live terminology server can change its answer tomorrow; terms.db cannot. A reviewer who reruns the pipeline against the same SQLite file gets the same codes — the entire reason the raw releases were downloaded once rather than queried live on every run.

Verified against the repository directly: requirements.txt, every top-level import across Part A and Part B, Part B/engine/package.json, and toolchain.available() executed live (returned True — the Java translator is compiled and callable, and RESULTS.md logs real compiler runs against it).
